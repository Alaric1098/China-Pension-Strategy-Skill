## 任务 A：`verify_design_docs.py` 敏感标识符误判

### 问题（已定位，非本次修改引入）

`verify_design_docs.py:40` 的正则：

```python
sensitive = re.compile(r"\b\d{17}[0-9Xx]\b|校验码[:：]\s*\S+|查询流水号[:：]\s*\S+|社会保障号码[:：]\s*\S+")
```

`\S+` 会匹配任何非空白字符，包括反引号。`docs/plans/2026-08-14-skill-polish.md:17` 在**列举禁止出现的字段名**时写了 `字符串 校验码： 与 查询流水号：`，于是被判为"文档泄漏敏感标识符"，`python verify_design_docs.py` 退出码 1。

这是**结构性误判**，不是个案：本项目的契约测试、SKILL 规范、隐私扫描器文档都必须能提到这些字段名，将来还会复现。

### 推荐方案（方案 1 + 方案 2 叠加）

1. **要求标签后跟真实值样式**：`\S+` → `[0-9A-Za-z一-鿿]{4,}`。反引号、句号、单字符都不再命中；真实泄漏（数字/字母/汉字串）仍然命中。
2. **扫描前剥离行内代码片段**：把 `` `...` `` 与围栏代码块替换为空白再扫描——元提及几乎总在代码片段里，这层让"讨论字段名"与"写出字段值"彻底分开。
3. **可测试化**：把正则与扫描逻辑提为模块级 `SENSITIVE_PATTERN` 与 `scan_sensitive(text) -> list[str]`，`main()` 调用它。

### 不推荐的备选（列出以便对比）

- **改写 `2026-08-14-skill-polish.md` 的措辞**：那是历史执行计划，改历史记录去迁就校验器；且下一份提到字段名的文档会再次触发。
- **把 `docs/plans/` 排除出扫描范围**：削弱真实防护面，方向相反。

### 文件

| 文件 | 动作 |
|---|---|
| `verify_design_docs.py` | 提取 `SENSITIVE_PATTERN` / `scan_sensitive()`；收紧正则；扫描前剥离行内代码与围栏代码块 |
| `tests/test_doc_verification.py` | 新建：元提及（`` `校验码：` ``、``查询流水号：`` 在代码片段内）判定为**干净**；真实样式（`校验码：A1B2C3`、`社会保障号码：110105199001011234`、17 位身份证）判定为**命中**；对全仓库 Markdown 跑一次 `scan_sensitive` 断言为空 |

## 任务 B：遗留 1 —— 广深失业保险费率（待 2026 年度基准费率）

### 现状

粤人社规〔2025〕50号 已核验（2026-01-01 施行、有效期 2 年、试点含广深、**自愿**参保），但办法只写"按照国家和省规定的失业保险基准费率（单位和个人费率之和）"。可查到 1% 的依据（粤人社函〔2023〕133号 转发件、国家延续文件）有效期均止于 2025-12-31，**2026 年度基准费率无可核验原文**。

### 建议：暂不建规则，改为"定义验收条件 + 定点复查"

盲目沿用 1% 会把一条已过期的费率写成当期事实，这正是本项目纪律要禁止的。建议：

1. **明确验收条件**（写入 references，作为将来补包的门槛）：来源须为 gov.cn 文本，且明确 2026 年度（或"继续执行至 XXXX"）的失业保险**基准费率数值**。优先级：国家人社部延续文件 > 广东省人社厅/税务局公告 > 广州/深圳市人社局费率页。
2. **一次定点复查**（只读，约 30 分钟）：查上述三级来源；命中则进入第 3 步，未命中则只更新 references 的复查记录与日期。
3. **命中后的建模形状**（现在先定好，避免将来临时决策）：
   - 规则 `guangzhou-flex-unemployment-contribution` / `shenzhen-flex-unemployment-contribution`，`MULTIPLY(base, rate)` → `monthly_unemployment_contribution`；
   - 失业基数口径（下限=所在市最低工资标准、上限=上年度在岗职工月平均工资 3 倍）与养老、医疗**均不同**，需另取两市最低工资与在岗职工月均工资来源；
   - 基数上下限的处理方式取决于**任务 C 的结论**（告警 or 钳制），故任务 B 应排在任务 C 之后。
4. **自愿参保的表达**：广深失业为自愿参保且需就业登记，不应默认计入月缴。建议规则落地时同时增加 `unemployment_enrolled` 事实（缺省 false），未声明参保则不输出失业缴费——避免把可选项当成默认账单。

### 文件（第 3 步命中后）

新增 2-4 条来源记录 + `references/regions/{guangzhou,shenzhen,guangdong}.md` 章节 + 两包各一条规则 + `schemas/person-input.schema.json` 的 `unemployment_enrolled` 事实 + 适配器映射 + 夹具。

## 任务 C：遗留 2 —— 缴费基数口径未钳制（不止医疗）

### 现状与一个更大的发现

深圳医保基数上下限（2026 年度 6727/33633）与养老基数（4775/27549）不同源；引擎按用户申报的单一基数 × 费率输出，不做钳制。

**排查中发现的既有问题**：各城包里的 `base_within_limits`（BOOLEAN 输出）**应用层从未消费**——`grep base_within_limits src/` 无命中，只存在于 11 个规则包里。也就是说，申报基数超出**养老**上下限时，引擎既不钳制也不告警，直接按越界基数算钱。这不是本次医疗费率引入的，是既有缺口，且比医保基数差异影响更大（养老是必填输出）。

### 建议：分两步，先补告警（推荐立即做），钳制另议

**C-1（推荐，低风险、修既有缺口）：申报基数越界告警**

- 应用层在解析规则后，读取规则 `parameters` 中的 `base_floor` / `base_ceiling`（养老，已存在）与 `medical_base_floor` / `medical_base_ceiling`（深圳医疗，任务 1-B 已写入），与申报基数比较；
- 越界时产出**非阻断警告**（`{code, message, related_refs}` 走既有 warnings 通道），例如 `CONTRIBUTION_BASE_BELOW_MEDICAL_FLOOR`；
- 数值输出不变 → **既有 run_id 全部不变**（warnings 是否进 input_digest 需在执行时确认，若进则改为仅出现在信封与报告，不进摘要）。

**C-2（较高保真、会改数值，建议暂缓）：真正钳制**

- 需要新增 `MIN` / `MAX` 运算符（形状比照已有的 `FLOOR_DIVIDE`/`POWER`：schema 枚举 + 求值器 + 操作数校验 + 单元测试）；
- 医疗规则改为 `MULTIPLY(MIN(MAX(base, floor), ceiling), rate)`；
- **后果**：深圳夹具 5000 基数低于医保下限 6727 → 医疗由 400.00 变为 538.16，深圳 run_id 改变；
- **阻碍**：广州只核验了医保基数**口径**（上上年度全口径月均工资的 60%-300%），**没有 2026 年度金额**，需补一条广州市医保缴费基数公告来源，否则广深钳制口径不对称。

建议先做 C-1；C-2 待广州基数金额到手、且你确认可以接受深圳数值变化后再单独审批。

### 文件（C-1）

| 文件 | 动作 |
|---|---|
| `src/china_pension_strategy/application/calculate_months.py`（或 `analyze.py` 的组装处） | 新增基数越界检查，产出 warnings |
| `tests/domain/test_calculation.py` 或新建 `tests/application/test_base_limits_warning.py` | 越界（低于/高于养老与医疗上下限）、边界值、无参数时不告警 |
| `docs/computation-and-reliability.md` | 记录告警语义（非阻断、不改数值） |

### 验证

全量 pytest 绿；北京 `run-a7440a1a…` 与其余各城 run_id 不变；深圳夹具信封出现越界警告且金额仍为 400.00。
