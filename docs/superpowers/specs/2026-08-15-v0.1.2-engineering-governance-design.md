# v0.1.2 Engineering Governance Design

## Goal

Release `v0.1.2` as a GitHub Pre-release that completes package/engine version separation, adds static quality gates, and establishes public security and contribution entry points without changing calculation semantics or existing `run_id` values.

## Scope

The release contains three independently reviewable work items:

- A new Issue for package release and engine semantics version separation.
- Issue #6: Ruff and type-checking quality gates.
- Issue #7: security policy, public Issue templates, PR template, and contribution governance.

Issues #1 through #5 and #8 remain open unless their tracker state changes independently. This release does not add policy values, change calculation rules, expand regional capability, or resolve the Guangzhou medical-policy expiry alert.

## Version Model

`PACKAGE_VERSION` identifies the distributed Python package and tool envelope. It must equal `project.version` in `pyproject.toml`.

`ENGINE_SEMANTICS_VERSION` identifies calculation, eligibility, capability-state, normalization, and structured-output semantics. It participates in content-addressed run identity.

For `v0.1.2`:

```text
PACKAGE_VERSION = 0.1.2
ENGINE_SEMANTICS_VERSION = 0.1.1
```

The Beijing golden run ID remains:

```text
run-95e2c71f61a9b8510cc4097e9c930d53afb36a4892be154802ac96c4687731e9
```

Package, adapter, renderer, documentation, CI, and governance version changes do not enter `run_id`. A ruleset update changes run identity through its content digest and does not by itself require an engine semantics bump.

## Quality Gates

Ruff provides formatting and static lint checks. Mypy provides type checking. Their configuration and constrained tool dependencies, including required third-party stubs, live in `pyproject.toml` under a `quality` optional extra. Contributors and CI install `.[test,quality]`, so local and remote checks use the same declared toolchain.

Ruff initially covers repository Python sources, tests, scripts, and root Python verification utilities. Mypy establishes a strict-enough production baseline over `src/china_pension_strategy`; test and script typing can be added incrementally without weakening the production gate. Neither tool may use global ignores, blanket error suppression, or broad exclusions to manufacture a green baseline. Narrow suppressions are allowed only when a concrete third-party or dynamic typing boundary is documented on the affected line.

CI retains the Python 3.12, 3.13, and 3.14 runtime test matrix. A separate named `Quality` job runs Ruff formatting, Ruff lint, and mypy on one supported Python version. This avoids repeating deterministic static checks in every interpreter job while preserving runtime support across all declared Python versions.

## Public Governance

`SECURITY.md` defines private vulnerability reporting and prohibits posting real pension records, identity data, contact data, financial accounts, credentials, or derived run artifacts in public Issues.

`.github/ISSUE_TEMPLATE/` contains separate bug, policy-update, and feature-request forms or templates. Each template requests synthetic reproduction data, affected region and capability, evidence requirements where relevant, and expected `run_id` impact.

`.github/pull_request_template.md` requires evidence, privacy, region, schema, ruleset, version, `run_id`, and test declarations. It explicitly requires confirmation that examples, fixtures, logs, and reproduction data are synthetic and contain no real-person or derived real-person artifacts. `CONTRIBUTING.md` becomes the public governance source and no longer requires contributors to read `.specify/memory/constitution.md`.

## Change Isolation

The release is implemented and reviewed in four slices:

1. Package/engine version separation and roadmap documentation.
2. Ruff and mypy configuration, resulting code fixes, CI, and contributor commands.
3. Security policy and public contribution templates.
4. Package version bump, changelog finalization, complete verification, tag, and Pre-release.

Formatting or typing fixes must remain behavior-preserving. If static analysis reveals a behavior defect, that defect is split into a separately tested semantic change and excluded from `v0.1.2` unless explicitly approved.

## Testing And Verification

Version contract tests prove that package metadata and engine defaults use separate identifiers. Regression tests prove adapter release metadata does not affect `run_id`, the tool envelope reports the package version, and the Beijing golden ID remains stable.

The release gate is:

```text
python -m ruff format --check .
python -m ruff check .
python -m mypy src/china_pension_strategy
python -m pytest -q
python verify_design_docs.py
python test_design_contracts.py
python audit_architecture.py --gaps
python scripts/policy_expiry_report.py --horizon-months 6
```

The policy expiry report remains an actionable maintenance signal. Its known #8 alert does not block this engineering-governance release, but any unexpected report failure does.

## Release Evidence And Supply Chain

The GitHub Pre-release is explicitly a non-production `LOCAL_MVP` engineering distribution; it does not grant `PRODUCTION_APPROVED` status to policy packages or outputs. The release notes and evidence state that independent production approval has not been granted. Production publication remains subject to the complete independent-review requirements in `docs/release-governance.md`.

A tag-triggered `Release` workflow builds the wheel and source distribution in isolation, scans dependencies and licenses, scans tracked content for secrets, generates a CycloneDX SBOM and SHA-256 checksums, verifies clean installation, upgrade from `v0.1.1`, rollback to `v0.1.1`, and historical golden replay, and creates a GitHub artifact attestation with OIDC. It publishes the verified files and retained evidence to the `v0.1.2` Pre-release. No long-lived signing key is generated or stored in the repository.

## Delivery

Each slice receives a focused commit. After local gates pass, push `main` and wait for `CI / Python 3.12 on Linux`, `CI / Python 3.13 on Linux`, `CI / Python 3.14 on Linux`, and `CI / Quality`. The scheduled `Policy expiry / Check current policy expiry` job remains visible but is not a `v0.1.2` release blocker while its known #8 alert is active. Create annotated tag `v0.1.2` only from the verified release commit. The tag-triggered `Release / Build, attest, and publish` job creates the Pre-release and supply-chain evidence; release notes state the version boundary, unchanged engine semantics and golden ID, non-production status, and known #8 alert.

Close #6, #7, and the new version-separation Issue only after the tagged commit contains their acceptance criteria. Do not close #8 as part of this release.
