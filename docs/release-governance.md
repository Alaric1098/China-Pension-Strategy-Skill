# 发布与兼容性治理

引擎、schema、规则包、地区适配器和报告模板独立版本化、独立审批。任何发布都必须通过可重复的发布门禁；不能以人工浏览一份示例报告代替自动校验。

## 语义化版本

所有可执行组件使用 `MAJOR.MINOR.PATCH` 语义化版本：

| 变化 | 版本 | 示例 |
|---|---|---|
| 不兼容的输入、输出、端口或规则语义变化 | `MAJOR` | 删除字段、改变月份计数含义 |
| 向后兼容的新能力 | `MINOR` | 新增可选场景字段或地区适配器 |
| 不改变契约的修正 | `PATCH` | 修复舍入错误或文案模板 |

政策规则包的法规生效日期不是版本号。追溯性更正即使法规日期不变，也必须发布新包版本并关闭旧包的事务有效期。报告模板变化若会隐藏、重命名或重新解释权威字段，至少提升次版本并重新执行契约测试。

### 发行版本与引擎语义版本

Python 包发行版本与计算引擎语义版本是两个独立标识：

- `PACKAGE_VERSION` 与 `pyproject.toml` 保持一致，按发行节奏提升；文档、CI、打包和社区文件变更可以只提升该版本。
- `ENGINE_SEMANTICS_VERSION` 只在计算、资格、能力状态、规范化或结构化输出语义可能变化时提升。
- `run_id` 包含 `ENGINE_SEMANTICS_VERSION`，但不包含 `PACKAGE_VERSION`、工具发行版本或适配器发行版本。规则变化已由规则包摘要进入运行身份。
- 仅修改展示、文档、CI 或分发元数据不得改变既有 golden `run_id`。提升引擎语义版本时必须记录受影响 ID，并保留前一引擎版本的只读重放能力。

## 兼容性矩阵

发布仓库维护机器可读兼容性矩阵，至少覆盖：

| 引擎 | 输入schema | 输出schema | 规则包 | 地区适配器 | 报告模板 |
|---|---|---|---|---|---|
| `1.4.x` | `1.x` | `1.x` | `>=2026.1,<2027.0` | `1.x` | `1.x` |

- 引擎启动时验证矩阵，缺少组合视为不兼容；
- `RuleSetPackage.engine_compatibility` 必须是矩阵允许范围的子集；
- 运行清单记录实际解析到的每个版本，不能只记录范围；
- 不兼容组合返回 `RULESET_INCOMPATIBLE`，不得自动降级；
- 支持窗口至少包含当前主版本和一个已发布前序主版本的只读重放能力。

## 发布门禁

### 政策包审核状态与环境门禁

政策包状态是运行时强制契约，不是展示标签：

- `PRODUCTION_APPROVED` 是唯一允许进入 `PRODUCTION` 执行并支持正式发布的状态。它要求完整权威来源追溯、schema与规则测试、领域审核、两名独立批准人、包签名和正式发布记录；提交者不能作为其唯一批准人。
- `MVP_REVIEWED` 仅表示官方来源追溯、摘要、schema校验、规则测试向量、回归测试和工程审核已完成。包必须声明 `local_only=true`、`execution_modes=["LOCAL_MVP"]` 且没有 `production_approval`。
- `MVP_REVIEWED` 只可在 `analysis_mode=LOCAL_MVP` 执行。应用层必须拒绝任何其他模式，不能自动降级、忽略状态或将其映射为 `PRODUCTION_APPROVED`。
- 使用任一 `MVP_REVIEWED` 包的运行不得进入 `PUBLISHED`；其状态上限为 `VALIDATED` 或 `RENDERED`，产物分类只能是 `S1-INTERNAL` 或 `S2-CONFIDENTIAL`。
- 每个此类结构化结果、工具引用的结果和渲染产物必须显示 `NOT_PRODUCTION_APPROVED`，记录 `MVP_REVIEWED` 包及摘要，并固定 `official_eligibility_claim=false`。输出不得形成官方资格认定。
- 候选、仅单次抽取、无稳定来源定位或未完成相应状态门禁的规则不可执行。无法由官方来源支持的条件必须产生 `UNKNOWN`、`BLOCKED` 或未支持结果，禁止默认猜测。

此本地MVP路径是独立、受约束的非生产生命周期，不豁免或缩减生产领域审核、双人批准、签名和正式发布要求。只有重新完成全部生产门禁并生成新状态、新摘要和批准轨迹后，包才可成为 `PRODUCTION_APPROVED`。

### 所有组件

1. 文档结构、JSON schema、链接和敏感信息检查通过；
2. 单元、集成、契约、架构和回归测试通过；
3. 依赖漏洞、许可证、密钥和恶意测试数据扫描通过；
4. 生成SBOM、内容摘要、签名和变更记录；
5. 独立审核人批准，提交者不能单独批准生产发布；
6. 在隔离环境完成安装、升级、回滚和历史重放演练。

### 计算引擎

- 月份边界、闰年、重复月份、负金额、舍入和跨地区转移测试通过；
- 首版至少包含25个确定性案例，并明确覆盖退休前59/60/61个月和累计179/180/181个月；
- 至少5个属性不变量，包括缴费月增加时剩余缺口不得增加、补贴增加时净支出不得增加，以及同输入同版本结果摘要完全一致；
- 至少3个双时态历史重放案例和8个端到端eval通过；
- 黄金案例的规范化结果摘要未发生非预期变化；
- 性能和内存不超过批准预算；
- 确定性测试在重复运行和不同支持平台产生相同结果。

### 政策规则包

- 每条规则均可追溯到权威来源片段和审批；
- 每个可执行包通过`policy-package.schema.json`校验，并且审核状态与执行环境匹配；
- 决策表没有重叠、空洞或未处理组合；
- 双时态、边界日期和追溯更正测试通过；
- 对受影响历史样本运行差异分析，并由政策审核人批准；
- 新旧版本同时可重放，不删除被替代包。

### 地区适配器

- 通过国家级端口契约和地区特有测试向量；
- 未支持字段显式返回，不用全国默认值静默替代；
- 权威来源、地区代码和经办角色映射得到复核。

### 报告模板

- 每个展示金额、日期、规则和推荐可追溯到结构化结果；
- `partial`、冲突、未知和政策歧义在所有格式中可见；
- DOCX/PDF生成通过可读性、字体、分页和无障碍检查；
- 模板不能覆盖结构化结果或隐藏阻塞项。

## 迁移与回滚

schema迁移使用显式、版本化、可逆的纯函数。迁移创建新对象和摘要，不修改历史运行。每个迁移包含输入/输出schema、前置条件、映射表、损失声明和往返测试。

回滚通过恢复前一签名组件版本和兼容性矩阵完成。已发布的错误结果不删除：将运行标记为已取代，创建修正子运行，并记录受影响案件、通知状态和政策/引擎差异。

## 工程预发布与非生产审批语义

GitHub 工程 Pre-release（例如 `v0.1.2`）只代表工程门禁已通过，不授予 `PRODUCTION_APPROVED`。即使 Pre-release 完整执行自动化扫描（依赖漏洞、许可证、密钥、SBOM、证明与安装/升级/回滚/重放演练），`LOCAL_MVP` 包仍受运行时状态门禁约束：使用 `MVP_REVIEWED` 包的运行不得进入 `PUBLISHED`，产物上限为 `S1-INTERNAL` 或 `S2-CONFIDENTIAL`。

任何生产发布仍必须独立完成领域审批：权威来源追溯、规则与 schema 测试、领域审核、两名独立批准人、包签名和正式发布记录，提交者不能单独批准。发行说明必须明确声明本次发布未授予独立生产审批。

## 发布证据

每次发布保留：版本、提交、构建环境、依赖锁、SBOM、测试摘要、覆盖范围、兼容性矩阵摘要、审批人、签名、发布时间和回滚目标。发布证据只包含合成测试标识，不包含真实案件数据。

## 首次实施顺序

1. 冻结领域类型、运行状态和首版JSON schema；
2. 实现纯领域计算及黄金案例；
3. 实现文件政策仓库、案件仓库和CLI入口；
4. 加入安全解析、审计、运行清单和保留作业；
5. 接入叙述和报告适配器；
6. 使用已审核的北京规则包完成本地MVP验证；只有通过完整发布门禁后才公开发布真实地区规则包和权威报告。

首个生产候选只支持一个明确制度和一个地区。其他地区返回“未支持”，避免以不完整通用逻辑制造看似精确的建议。
