# China Pension Strategy Skill

中国养老保险计算与续保策略技能设计稿。项目目标是把分散的国家政策、地方经办规则、个人缴费记录和现金流假设转化为可复核的月度计算与动态决策建议。

> 当前状态：`LOCAL_MVP` 已实现 10 个可选城市路由（北京、上海、广州、深圳、杭州、成都、武汉、南京、天津、重庆）。杭州、成都、武汉、南京分别通过浙江、四川、湖北、江苏省级政策包解析养老缴费规则；这些省级层不是独立的 `region` 取值。北京路由还支持待遇测算，CLI、隐私、保留、审计、测试与评估门禁均已实现。

## 免责声明

本工具只提供信息整理、确定性测算和决策支持，不替代社保经办机构的缴费年限核定、资格认定、退休审批或法律意见。政策数据具有地区差异和时效性；办理缴费、补缴、转移、退休或补贴申请前，必须核对最新官方规则并向主管经办机构确认。

需要 Python 3.12 或更高版本：

```powershell
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install -e ".[test]"
```

## 快速开始

以下命令只使用 `evals/fixtures/` 中从零构造的合成数据；人物属性、日期组合、金额和标识符均不取自、改写自或扰动自任何真实个人或权益单：

```text
china-pension validate --input evals/fixtures/golden-beijing-flex-2026.json
china-pension analyze --input evals/fixtures/golden-beijing-flex-2026.json --runs-dir runs
china-pension render --run-id run-95e2c71f61a9b8510cc4097e9c930d53afb36a4892be154802ac96c4687731e9 --runs-dir runs --format markdown
```

`analyze` 会向标准输出写入版本化 JSON 信封，并在 `runs/<run_id>/` 保存结构化结果与运行清单。`render` 只读取该冻结结果，不重新解释政策或计算金额。

## 数据时效

政策包和其中的规则均带有效期。维护者应定期运行：

```text
python scripts/policy_expiry_report.py
```

截至 2026-08-14，广州医疗费率规则将在 2026-12-31 到期。临近或已经到期的当前规则必须更新、重新审核并发布新版本；历史包继续保留用于重放，但不参与当前时效门禁。

## 项目定位

本项目不是通用理财顾问，也不是静态养老政策百科。它面向中国基本养老保险的实际决策场景，重点解决缴费记录对账、最低年限判断、灵活就业续缴、补贴申请时点、现金流比较和政策不确定性管理。

当前版本支持 10 个城市路由及其规则包。国家规则、省级政策层、城市规则和个人事实保持分层；新增地区通过适配器和独立规则包扩展，不修改核心计算逻辑。待遇测算当前仅由北京路由接入，端到端路径使用全国待遇规则和显式计发基数输入，不代表已经覆盖全国待遇测算。

公开技能生态中已有通用养老金、保险顾问和中国家庭财务规划技能，但较少有工具同时处理中国基本养老保险、地方社保规则、个人权益单、灵活就业补贴和月度现金流。本项目的差异化方向是“证据驱动的政策计算与决策”，而不是泛化问答。

## 解决的问题

典型任务包括：

- 从个人权益记录中提取实际缴费月数、累计年限、缴费基数、个人账户余额和单位变动记录。
- 解释权益单明细月数与累计年限换算结果之间的数据冲突，并输出待核验项目。
- 按退休年份计算最低缴费年限和剩余缺口。
- 比较最低基数续缴、较高基数续缴、暂缓缴费和持续缴至退休等方案。
- 计算灵活就业养老、医疗、失业保险缴费及补贴后的个人净负担。
- 比较提前申请补贴与进入退休前5年后申请的现金流、月份和政策风险。
- 判断电话答复、政策问答、规范性文件和个人陈述的证据等级。
- 在政策、资格或现金储备变化时给出可执行的策略切换条件。

## 设计原则

### 事实、规则与假设分离

用户提供的数据不自动视为官方认定，电话答复不自动升级为公开政策，模型预测不写成未来账单。输出必须分别标注个人事实、官方规则、经办参考、计算假设和待核验事项。

### 计算可复现

金额使用 `Decimal` 计算，缴费年限按月计算，申请与退休边界使用明确的首尾月份。图表只读取计算引擎的结构化结果，不在多个文件中重复硬编码金额。

### 地区规则可替换

国家最低缴费年限等规则放入国家层；缴费基数、补贴条件、医保要求和经办流程放入地区层。计算引擎通过统一接口读取地区参数。

### 建议是条件式决策

技能不输出脱离风险偏好的唯一答案。推荐结果应包含适用条件、现金要求、阈值或情景假设、失败情景和切换规则。没有匹配人群、事件定义和有效日期的可信统计时，不把用户输入或模型假设写成客观成功概率。

### 保守处理证据缺口

数据冲突或政策证据不足时，技能保留多个口径并采用更保守的现金或缴费假设，同时给出向12333、12345或经办机构核验的具体问题。

## 技能触发范围

建议技能名称为 `china-pension-strategy`。

建议触发描述：

```yaml
---
name: china-pension-strategy
description: Use when analyzing Chinese basic pension insurance, social-security contribution records, retirement contribution gaps, flexible-employment continuation, pension subsidy timing, regional pension rules, or comparing contribution and retirement strategies in China.
---
```

应触发的用户表达包括：

- “帮我算养老还差多少个月。”
- “灵活就业养老应该按最低基数还是提高基数？”
- “北京退休前5年社保补贴什么时候申请更划算？”
- “权益单明细月数和累计年限为什么对不上？”
- “失业金期间继续缴养老会不会影响待遇？”
- “比较停缴、续缴和缴到退休的现金流。”

不应触发的场景包括商业养老保险产品推荐、股票基金投资建议、其他国家养老金制度，以及仅需查询单个政策网页但不涉及个人养老计算的任务。

## 数据流

```text
用户问题或权益文件
        ↓
隐私识别与脱敏
        ↓
缴费记录结构化
        ↓
月度记录对账与冲突检测
        ↓
国家规则 + 地区规则 + 有效日期核验
        ↓
缴费、补贴、退休和现金流场景计算
        ↓
风险门槛与动态策略
        ↓
事实表、方案表、图表、建议和核验清单
```

每一步都应保留输入来源和计算依据。下游结论必须能够追溯到原始字段、政策条款或显式假设。

## 输入数据模型

输入字段不采用全局“必需/非必需”二分，而用 `required_for` 声明它阻塞的分析能力。每项能力返回 `AVAILABLE`、`PARTIAL` 或 `BLOCKED`；缺少精确测算字段时，仍可输出有明确限制的策略初筛。

### 个人信息

| 字段 | `required_for` | 说明 |
|---|---|---|
| 出生年月或已确认退休时间 | `exact_retirement_boundary`、`subsidy_window_analysis` | 用于计算法定退休时间和退休前5年边界 |
| 性别及人员类别 | `statutory_retirement_projection` | 延迟退休和地区规则可能需要 |
| 管辖角色及有效期间 | `regional_rule_resolution` | 不以单一“参保地区”代替缴费地、补贴服务地和待遇核定地 |
| 当前就业状态 | `employment_related_eligibility` | 在职、失业、灵活就业或其他 |
| 失业待遇起止时间 | `unemployment_overlap_analysis` | 判断医保代缴和策略窗口 |
| 风险偏好 | `recommendation_ranking` | 缺少时使用明确声明的默认目标，不影响事实计算 |

### 缴费信息

| 字段 | `required_for` | 说明 |
|---|---|---|
| 各险种实际缴费月数 | `exact_gap_calculation` | 优先读取月度明细或权益单合计 |
| 累计缴费年限 | `preliminary_gap_screening`、`reconciliation` | 与实际月数分别保留，不强行合并 |
| 缴费起止年月 | `reconciliation` | 用于检测缺口、重复和跨月边界 |
| 历年缴费基数 | `pension_projection` | 用于历史轨迹和养老金测算 |
| 个人账户余额及截止日期 | `pension_projection` | 两项必须同时记录 |
| 补缴、转移、视同缴费 | `recognized_service_assessment` | 解释汇总与明细差异 |

原始身份证号、社会保障号码、银行卡号、校验码和查询流水号不进入分析数据模型。

## 政策证据模型

| 等级 | 来源 | 使用方式 |
|---|---|---|
| A | 法律、国务院文件、部委或地方正式规范性文件 | 可作为规则基线，仍需检查有效日期和地区 |
| B | 政府官网政策问答、办事指南、官方解读 | 可解释经办流程，不覆盖更高等级文件 |
| C | 经办机构书面回复、可查询工单、短信答复 | 可用于个人案件，但应记录服务地和日期 |
| D | 电话咨询或现场口头答复 | 仅作为风险提示或保守假设，不写成公开政策定论 |
| E | 用户推测、媒体内容、模型假设 | 只能用于情景分析，不能作为资格结论 |

每条政策规则至少保存 `jurisdiction`、`source_url`、`document_number`、`published_at`、`effective_from`、`effective_to`、`retrieved_at` 和 `evidence_level`。过期规则不能静默参与计算。

证据元数据不等于可执行规则。计算只读取已批准的 `PolicyRule`、`DecisionTable` 和 `ParameterTable`；每条规则具有稳定ID、制度、管辖角色、条件、输出、有效时间、事务时间、来源片段和显式 `RuleOverride`。解析器依次按制度、管辖角色、双时态、法律层级、显式覆盖、兼容性和发布状态缩小候选集，不能消除的不兼容结果返回 `AMBIGUOUS_POLICY_RULE`。

## 计算引擎

### 月度年限

缴费年限统一转换为月数：

```text
总月数 = 年数 × 12 + 月数
剩余月数 = 法定最低月数 - 已确认累计月数
```

起止年月采用首尾月份均计入的规则，并与权益单“实际缴费月数”交叉核验。二者不一致时，输出差异，不覆盖原始值。

### 灵活就业缴费

```text
适用规则包 = resolve_policy_rules(制度, 管辖角色, 有效日期, 已知时间)
月度缴费与补贴 = deterministic_rule_evaluator(PolicyRule, DecisionTable, ParameterTable, 个人事实, 月份)
个人净负担 = 实际缴费额 - 实际补贴额
```

核心引擎和地区适配器都不硬编码全国通用补贴公式。`PolicyRepository` 提供已批准规则包，规则解析器选择适用版本，地区适配器只提供管辖枚举和映射，确定性求值器执行地区规则。养老、医疗和失业保险分别计算、分别取整，再汇总。计算结果必须注明使用的地区、年度、最低基数、费率、规则ID和四舍五入规则。

### 个人账户

个人账户测算应区分单位就业和灵活就业身份。进入个人账户的金额不等于个人实际支付的全部灵活就业养老费用。模型还需记录个人账户余额的截止日期、后续记账利率假设和退休计发月数。

### 现金流与敏感性

每个方案按月生成：

```text
月份、缴费身份、缴费基数、养老缴费、医疗缴费、失业缴费、补贴、个人净支出、累计支出
```

敏感性参数至少包括基数增长率、折现率、补贴延续情景、资格保持情景、审核结果情景和最后缴费月。只有当前有效、经过批准且事件定义和适用人群匹配的官方统计才能表示为证据支持的概率；其他数值必须标记为用户假设、专家假设或纯情景参数。没有可信概率时使用阈值、范围或保守/基准/乐观情景。金额和时间价值应分别展示，避免只比较未来名义总额。

## 续保策略引擎

策略引擎先验证硬约束，再比较目标函数。

资格判断采用三值模型 `ELIGIBLE`、`INELIGIBLE`、`UNKNOWN`。输出分别列出已满足、已失败和未核验条件；存在未核验条件且没有失败条件时不得返回 `ELIGIBLE`。

硬约束包括最低缴费年限、法定退休时间、参保地区、个人资格和不可重复申请规则。目标函数可以选择：

- 最低合规成本：确保达到领取养老金最低年限。
- 现金流稳定：降低近期全额缴费压力。
- 补贴最大化：在资格和政策可持续的条件下增加补贴月份。
- 养老金提升：提高缴费年限或基数。
- 确定性优先：降低政策变化和资格丧失风险。

推荐结果不只给出一个日期，而是给出策略切换条件。例如：

```text
若现金储备能够覆盖未来30个月全额缴费，且在已声明的政策、资格和审核情景范围内等待方案仍高于盈亏平衡门槛，则继续等待；否则提前申请。情景权重是用户或审核人批准的敏感性参数，不代表统计概率。
```

策略应至少每6个月复核一次。国家或地区政策更新、就业状态变化、缴费失败、现金储备下降和资格认定变化都应触发立即复核。

## 标准输出

技能输出采用固定结构：

1. **结论摘要**：当前建议、适用条件、最大风险和政策核验日期。
2. **能力与资格**：每项能力的 `AVAILABLE/PARTIAL/BLOCKED` 状态，以及资格的 `ELIGIBLE/INELIGIBLE/UNKNOWN` 条件明细。
3. **已确认事实**：个人记录和官方规则，分别注明来源日期。
4. **数据冲突**：明细、汇总和用户陈述之间的差异。
5. **缺失信息**：缺少字段所阻塞或降低精度的具体能力。
6. **政策证据表**：规则、地区、有效日期、已知时间、等级和来源链接。
7. **缴费缺口**：按不同口径计算的最低剩余月数。
8. **方案现金流表**：缴费、补贴、净支出和累计金额。
9. **敏感性分析**：增长率、折现率、阈值、范围和情景变化。
10. **推荐策略**：基准方案、保守方案、依赖能力和切换条件。
11. **办理清单**：需要向经办机构确认的具体问题。

输出中的每个金额都应能够回溯到公式和参数；每个政策结论都应能够回溯到来源和有效日期。

## 隐私与安全

- 读取文件后立即识别身份证号、社会保障号码、银行卡号、手机号码、校验码和查询流水号。
- 默认只在内存或系统临时目录处理原始文件，不把私人副本写入项目目录。
- 日志记录字段名称和问题类型，不记录完整身份值。
- 示例、测试夹具和公开仓库只使用从零构造且不源自真实权益记录的合成数据。
- 原始接入、规范化事实、日志、外部服务和报告分别执行 `ALLOW`、`REDACT` 或 `BLOCK`；无法安全最小化的数据返回 `PRIVACY_POLICY_VIOLATION`。
- 不自动上传用户文件，不配置远程仓库，不在未经同意时调用第三方服务处理权益文件。

## 测试与评估

技能应采用“无技能基线”和“加载技能后”对照测试。第一批测试场景建议包括：

| 场景 | 预期行为 |
|---|---|
| 合成权益记录的明细月数与汇总月数不一致 | 保留两个口径，报告差异并要求月度明细 |
| 领取失业金期间自行缴养老 | 区分养老续缴与失业待遇停止条件，不猜测补贴能否重叠 |
| 退休前5年申请补贴 | 使用初次核定、次月起算和退休月边界 |
| 用户来自非北京地区 | 不套用北京规则；已支持城市选择对应路由，其他地区要求新增适配器 |
| 电话答复与公开文件不一致 | 降低电话答复证据等级，保留书面核验任务 |
| 缺少出生年月或退休时间 | 停止给出精确月份，先请求必要信息 |
| 权益文件含身份证号 | 输出脱敏结果，测试夹具不保留真实号码 |
| 政策超过有效期 | 阻止旧规则参与基准计算并要求更新来源 |

机械断言至少检查：月数换算、金额公式、四舍五入、来源日期、地区隔离、隐私脱敏、图表与表格一致性，以及同一结论在摘要和正文中没有冲突。

## 实施路线

开放 Issues 的优先级、依赖、目标版本、逐项验收标准和共同验证门禁见 [Issue 修改路线图](docs/issue-roadmap.md)。GitHub Issue tracker 仍是工作状态和讨论结论的唯一来源。

### 当前 `LOCAL_MVP` 地区与能力范围

已实现 10 个可选城市路由：北京、上海、广州、深圳、杭州、成都、武汉、南京、天津和重庆。十城均覆盖灵活就业养老、医疗及补贴规则；杭州、成都、武汉、南京的养老缴费分别通过浙江、四川、湖北、江苏省级包解析，城市层提供医疗和补贴，这四个省级层不是独立的 `region` 取值。失业缴费仅北京有可执行规则，其他城市按部分能力处理。`PENSION_ESTIMATION` 当前仅由北京路由接入，端到端路径使用全国待遇规则和显式计发基数输入，尚不宣称完整北京地方待遇或全国待遇覆盖。

### 阶段二：证据与政策更新

增加政策有效期检查、来源快照、变更提醒和书面答复记录。政策更新不能直接覆盖旧规则，应保留版本和适用期间。

### 阶段三：地区持续扩展

在现有十城路由和统一地区接口上继续增加经过验证的城市及省级政策层。新增地区必须具备独立规则包、来源证据、有效期门禁和合成端到端夹具，不能将现有十城能力表述为全国覆盖。

### 阶段四：报告与可视化

将现金流、缴费缺口和敏感性分析输出为Markdown、JSON和可选DOCX/PDF。图表必须读取同一计算结果对象，不能维护另一份数据。

### 阶段五：公开发布

完成合成数据替换、隐私扫描、许可证选择、贡献指南、安全说明、触发描述测试和技能打包。公开版本不得包含真实个人权益文件或由其派生的可识别数据。
